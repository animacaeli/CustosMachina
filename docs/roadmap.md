# CustosMachina 演进路线图

> 定稿：2026-09-28（基于第四阶段收尾评审 + 后续方向讨论）
> 性质：跨阶段主线路由文档；各阶段实施前另立详细计划（如 plan-phase4-runtime.md）。
> 项目初衷：**机器守护者**——用 AI 把运维功能与数据串联起来，AI 是主线而非装饰。

## 一、定位与原则（所有阶段的决策基准）

1. **自托管轻量运维平台**：单实例假设（调度/通知横切均为进程内语义，HA 需求出现再做 DB 级抢占）。
2. **自建"调度与权限壳"，复用成熟引擎**：不自研 ACME/告警引擎/编辑器内核；也不内嵌重型平台（jumpserver/certimate UI）——能外链的成熟界面外链（O2），需要权限与审计统一的自建 UI（AgileConfig、告警模板）。
3. **compose 期能力边界**：不自建 K8s 已有的东西（滚动更新/服务发现/ingress）；转 k3s 判据不变（≥3 台主机等多机需求、真实滚动更新需求、弹性调度需求、观测超 5 台主机）。
4. **AI 三条铁律**：后端中转（key/脱敏/权限一致）；OpenAI 兼容协议、endpoint/model 可配置（自托管小模型与云 API 通吃）；**advisory 先行、autonomous 后置**（AI 结论标注"建议"，执行权在人与既有权限模型）。
5. 每阶段穿插消化审核欠账（当前 #33~38，见审核留档清单）。

## 二、已完成（P1~P4 概览）

- P1 骨架与基建：monorepo（vben + wire 模块化）、三级角色 + casbin、双 token、IM 登录（企微扫码/钉钉）、docker-compose 一键部署、单镜像发版。
- P2 资源管理：agentless SSH（TOFU）、指标采集、容器/终端（审计/超时/会话上限）、compose 部署与灰度承载。
- P3 环境管理：gitea 原生 CI + webhook 兼容、registry、发布/回滚、灰度策略（map/split_clients）、测试槽位、真机 e2e。
- P4 运行时：定时任务+脚本库（标准 crontab/仅手动/快速执行/实时日志/失败重试/重试通知/全量日志下载/蓝绿活跃色跟随）、蓝绿发布（任务化进度/健康门禁/conf 单写者）、观测组件一键部署、SFTP、约定文档。质量闭环：深审→真机→UI 三轮验证修复。

## 三、P5（下一阶段，建议周期 4~6 周）

主线四条产品线 + 一块底座，共享基建（Monaco 编辑器、统一通知路由、SSH 通道、cron 调度、AI 中转层）：

### 1. O2 观测闭环 + 统一告警路由（P0）
- 告警模板自研 UI，调 O2 alerts API 同步；通知走平台 notify（**统一路由规则**：cron 失败/观测失败/O2 告警/证书到期同一出口同一配置）。
- 日志/仪表盘外链 + 透传认证（免登，半小时级）。
- 补 vector→O2 实际投递验证（P4 遗留）。
- 链路追踪：**不做**（等业务先接 OTel SDK）。

### 2. AgileConfig 配置中心接入（P0）
- OpenAPI + 后端中转自建 UI；密钥查看/修改权限分离、敏感值默认脱敏、全程审计。
- Monaco 编辑器基建（json 默认视图 + yaml/toml 多视图），复用到 cron 脚本编辑、SFTP 在线编辑。
- 对齐遗留：测试槽位配置由配置中心接管（原 slot_overrides 移除欠账）。
- 服务注册发现：**P6 再评估**（单机 compose 需求弱，且会搅动现有 external network 接入规范）。

### 3. 证书自动续期与发放（P1，自研轻量，不接 certimate）
- lego（ACME）DNS challenge 申请/续期；续期调度复用 cron；发放复用 SSH + nginx -t/reload 通道；到期告警走通知横切。
- 解决遗留 #16（生产 HTTPS 未配）。iframe 内链 certimate 明确否决。

### 4. 堡垒机语义补齐（P1，不部署 jumpserver）
- 终端权限按主机/分组细粒度（casbin 加资源点）。
- 会话审计回放 UI（asciinema 格式，消化遗留 #20/#38）。
- **不做**：MFA、双人复核、授权窗口——避免蔓延成自研 jumpserver。

### 5. 备份与恢复（本次评审新增，P0.5）
- 数据库定时备份（cron 调度 + SSH 执行 + 失败通知 + 保留期清理——复用 cron_runs 生命周期模式）。
- 备份目标：本地轮转 + 对象存储（MinIO/S3 兼容，见生态接入）。
- 恢复演练文档与一键恢复脚本；**平台自身备份**（DB + compose 目录 + 密钥导出/恢复）一并做。

### 6. AI 顾问层试点（P5 内启动，见第五节 AI 规划）
- 两个场景先行：告警诊断摘要、蓝绿/部署变更审核建议。

## 四、P6（按需启动）

- AgileConfig 服务发现（compose 期可选能力）。
- IM 机器人双向（查状态/确认告警，与 AI 对话入口融合）。
- AI 自然语言 → 操作（带人工确认层）。
- k3s 主线（触发判据满足后另立计划）。
- 前端技术债收口（#33 composable 抽取等）。

## 五、AI 规划（主线，分两批 + 对话 UI）

### 架构底座（P5 落地）
- **AI 中转层**：后端模块（OpenAI 兼容协议），provider/model/endpoint/key 可配置；审计与用量记录；与 AgileConfig 中转共用鉴权/脱敏基建。
- **上下文供给层（Context Pack）**：平台把特权上下文打包成结构化供给——主机清单/状态、项目与发布历史、容器与指标、cron 输出与审计、配置快照、告警事件。**这是本平台做 AI 的护城河：通用助手要用户贴日志，我们手里有全量结构化上下文。**

### 场景批次
- **第一批（advisory，P5）**：告警诊断摘要（通知附带上下文打包 + AI 归因建议）；变更审核（compose diff 审查：healthcheck 缺失/端口冲突/资源限制/迁移风险）；失败归因与模板生成（cron 脚本/告警模板/compose 片段）。
- **第二批（确认层，P6）**：自然语言 → 平台操作（解析为待执行操作，人确认后走既有权限与审计执行）。

### 独立对话 UI（DeepSeek 网页形态，用户 2026-09-28 补充规划）
- 纯对话前端：流式输出（SSE）、多会话管理、Markdown/代码块渲染。
- 双模式：
  - **通用 Agent 对话**：不接平台数据，纯模型对话（也用于配置调试）。
  - **平台上下文对话**：会话可挂载 Context Pack（选择项目/主机/时间窗），AI 回答基于平台实时数据；后续演进为对话内工具调用（只读查询先行，写操作走确认层）。
- 前端组件复用：Monaco（代码块编辑）+ 通知路由（对话中触发的告警查询）。
- 实施顺序：中转层 → Context Pack（只读）→ 对话 UI → 顾问场景挂接。

## 六、生态通用化（开源适配层，用户 2026-09-28 补充规划）

目标：作为开源项目让更多人可用，把强绑定生态改为**可插拔 provider**。原则：接口在本仓定义，适配器按需注册，能力探测 + 配置驱动，未配置时优雅降级。

| 绑定点 | 现状 | 通用化方向 | 优先级 |
|---|---|---|---|
| Git 服务（CI 源） | gitea 原生 API + webhook 兼容层 | GitProvider 接口（gitea/forgejo/gogs API 高度兼容，一家适配器通吃；GitHub/GitLab 另立适配器） | 高（开源用户第一门槛） |
| IM 通知 | 企微/钉钉/飞书三家 | 已是插件式；补 Telegram/邮件(SMTP) 适配器 | 高（海外用户） |
| IM 扫码登录 | 企微 CorpApp / 钉钉 | OAuthProvider 接口化，同样补 GitHub OAuth | 中 |
| 观测后端 | OpenObserve | ObservBackend 接口（告警模板/日志查询/外链生成），Grafana/Loki 适配器 | 中（P5 告警同步时顺手定义接口） |
| 配置中心 | AgileConfig（P5 接入） | 接入时即按 ConfigProvider 接口设计，不写死 | 高（P5 时直接做对） |
| 对象存储 | （P5 备份引入） | S3 兼容协议为标准（MinIO/云 OSS/阿里 OSS 全覆盖），无需多适配 | 低 |
| ACME DNS | lego 自带全量 provider | 无需自研 | — |
| 镜像仓库 | docker registry 协议 | 已通用（harbor 等兼容） | — |

配套开源化工作：部署文档参数化（生态选择矩阵）、demo 项目/种子数据中立化（去个人域名）、README 英文化。**放在 P5 后半~P6，先在 P5 的新模块（告警/配置中心）上直接按接口写，老模块（gitea CI）逐步抽。**

## 七、生态接入候选（仅轻量级，2026-09-28 评估）

| 候选 | 用途 | 接入方式 | 结论 |
|---|---|---|---|
| MinIO / S3 兼容 | 备份目标存储 | 后端 SDK（S3 协议） | **采纳**（P5 备份配套） |
| Uptime Kuma | 拨测/可用性监控 | API 或外链 | 候补（告警路由落地后评估是否被 O2 告警覆盖） |
| frp | 内网穿透 | 已在用（宿主部署） | 维持现状，不入平台 |
| Grafana/Loki | 观测替代栈 | ObservBackend 适配器 | 仅作开源用户可选项，不自荐 |
| n8n / 重型编排 | 自动化编排 | — | **不做**（与平台定位重叠且重） |

## 八、不做清单（有意取舍，防范围蔓延）

工单/变更审批流、多租户、成本管理、漏洞扫描、CMDB 自动发现、SLA 管理、jumpserver 级堡垒能力（MFA/双人复核/授权窗口）、自研告警引擎、自研 ACME、内嵌重型平台 UI、链路追踪（业务接 OTel 前）、平台多实例 HA（需求出现前）。

## 九、执行纪律

- 每阶段：详细计划文档 → 实施 → 深审 → 真机 + UI 双验证 → 收尾评审（沿用 P4 质量闭环）。
- 优先级冲突时：**备份/数据安全 > 通知/告警（知情权）> 自动化便利 > 界面体验**。
- 新功能一律过"开源适配层"审视：新模块直接按 provider 接口写。

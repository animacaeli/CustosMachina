# CustosMachina 演进路线图

> 定稿：2026-09-28（基于第四阶段收尾评审 + 后续方向讨论）
> 修订：2026-10-01 新增"配置文件管理"产品线（P5 §2）；AgileConfig 定位降为文件方案的补充（P0→P1）；多配置中心生态明确不做（见第六节决策记录）。
> 性质：跨阶段主线路由文档；各阶段实施前另立详细计划（如 plan-phase4-runtime.md）。
> 项目初衷：**机器守护者**——用 AI 把运维功能与数据串联起来，AI 是主线而非装饰。

## 一、定位与原则（所有阶段的决策基准）

1. **自托管轻量运维平台**：单实例假设（调度/通知横切均为进程内语义，HA 需求出现再做 DB 级抢占）。
2. **自建"调度与权限壳"，复用成熟引擎**：不自研 ACME/告警引擎/编辑器内核；也不内嵌重型平台（jumpserver/certimate UI）——能外链的成熟界面外链（O2），需要权限与审计统一的自建 UI（AgileConfig、告警模板）。
3. **compose 期能力边界**：不自建 K8s 已有的东西（滚动更新/服务发现/ingress）；转 k3s 判据不变（≥3 台主机等多机需求、真实滚动更新需求、弹性调度需求、观测超 5 台主机）。
4. **AI 五条铁律**：后端中转（key/脱敏/权限一致）；OpenAI 兼容协议、endpoint/model 可配置（自托管小模型与云 API 通吃）；**advisory 先行、autonomous 后置**（AI 结论标注"建议"，执行权在人与既有权限模型）；**Context Pack 按调用者角色过滤**（dev 的 pack 不含 prod 配置与全量日志——对话入口不得成为绕过 casbin 的只读超权）+ **DLP 清单**（凭据/密钥/ticket/手机号等永不入 pack，启动时校验拦截）；**Prompt 注入对策**（pack 内容一律以声明"不可信输入"的数据块包裹，NL→查询的结果在返回前再过一次权限过滤）。
5. 每阶段穿插消化审核欠账（当前 #33~38，见审核留档清单）。

## 二、已完成（P1~P4 概览）

- P1 骨架与基建：monorepo（vben + wire 模块化）、三级角色 + casbin、双 token、IM 登录（企微扫码/钉钉）、docker-compose 一键部署、单镜像发版。
- P2 资源管理：agentless SSH（TOFU）、指标采集、容器/终端（审计/超时/会话上限）、compose 部署与灰度承载。
- P3 环境管理：gitea 原生 CI + webhook 兼容、registry、发布/回滚、灰度策略（map/split_clients）、测试槽位、真机 e2e。
- P4 运行时：定时任务+脚本库（标准 crontab/仅手动/快速执行/实时日志/失败重试/重试通知/全量日志下载/蓝绿活跃色跟随）、蓝绿发布（任务化进度/健康门禁/conf 单写者）、观测组件一键部署、SFTP、约定文档。质量闭环：深审→真机→UI 三轮验证修复。

### 1. O2 观测闭环 + 统一告警路由（P0｜自用刚需）
- 告警模板自研 UI，调 O2 alerts API 同步；通知走平台 notify（**统一路由规则**：cron 失败/观测失败/O2 告警/证书到期同一出口同一配置）。
- 路由规则最小能力集（防膨胀为消息中台）：目标分组、静默时段、按严重级别分流、同类告警聚合窗口。**不做**：升级链、值班表、多渠道编排。
- 日志/仪表盘外链 + 透传认证（免登，半小时级）。
- 补 vector→O2 实际投递验证（P4 遗留）。
- 链路追踪：**不做**（等业务先接 OTel SDK）。

### 2. 配置文件管理（P0｜开源门面为主，2026-10-01 新增）
- 动机：不是所有项目都需要接配置中心——compose 期绝大多数项目的配置就是 `config.yaml` / `.env` 挂 volume 的普通文件，平台不能把这部分最普遍的场景排除在外。
- 能力：文件级配置的存储/编辑/版本/审计/下发（yaml/json/toml/.env），敏感文件默认脱敏，权限走 casbin；下发复用 SSH/SFTP 通道。
- 编辑器直接复用 Monaco 基建（P4 已铺完，与 cron 脚本/SFTP 在线编辑同源），实现成本低。
- **热更新的边界要明确**：文件热更新是应用自身的行为（Viper WatchConfig / Spring @RefreshScope / SIGHUP 重载），平台不承诺等价于配置中心 SDK 的热更体验。下发后提供可选的生效动作：SIGHUP / 调 refresh 端点 / 重启容器（平台已有容器重启能力），未实现监听的应用走重启——无需重新发布，前提是配置以 volume 挂载而非打进镜像。
- 与配置中心的关系：**文件真相源归本模块，K/V 拉取式（SDK 热更/多应用共享）归 AgileConfig**，两者共用权限/审计/脱敏/Monaco 基建，且**共用同一套配置管理 UI**——UI 只面向平台模型，文件与 AgileConfig 是两种可插拔底层（见 §3 的解耦要求）。模块归属独立（参考三阶段"projects 独立模块不放资源管理"先例），仅复用资源管理的 SSH 通道。

### 3. AgileConfig 配置中心接入（P1｜开源门面为主、自用为辅，定位为文件方案的补充）
- OpenAPI + 后端中转自建 UI；密钥查看/修改权限分离、敏感值默认脱敏、全程审计。
- **UI 与底层解耦（硬性要求，2026-10-01 补充）**：配置管理的前端与平台 API 只面向平台自有领域模型（应用/环境/配置项/版本/审计/脱敏），AgileConfig 是纯后端 provider——替换或移除底层时 UI 零改动。AgileConfig 特有能力（节点状态/客户端在线）作为 provider 可选能力暴露，UI 缺失时优雅降级。这也意味着"UI 不变、只换底层"的诉求天然催生了 provider 接缝——此处抽象不是投机（rule of two 例外），因为它服务于已明确的换底需求（含止损回退内建方案的场景）。
- Monaco 编辑器基建（json 默认视图 + yaml/toml 多视图），复用到 cron 脚本编辑、SFTP 在线编辑。
- 对齐遗留：测试槽位配置由配置中心接管（原 slot_overrides 移除欠账）。
- 服务注册发现：**P6 再评估**（单机 compose 需求弱，且会搅动现有 external network 接入规范）。

### 4. 证书自动续期与发放（P1｜自用刚需，自研轻量，不接 certimate）
- lego（ACME）DNS challenge 申请/续期；续期调度复用 cron；发放复用 SSH + nginx -t/reload 通道；到期告警走通知横切。
- 解决遗留 #16（生产 HTTPS 未配）。iframe 内链 certimate 明确否决。

### 5. 堡垒机语义补齐（P1｜开源门面为主，不部署 jumpserver）
- 终端权限按主机/分组细粒度（casbin 加资源点）。
- 会话审计回放 UI（asciinema 格式，消化遗留 #20/#38）。
- **不做**：MFA、双人复核、授权窗口——避免蔓延成自研 jumpserver。

### 6. 备份与恢复（P0.5｜自用刚需，本次评审新增）
- 数据库定时备份（cron 调度 + SSH 执行 + 失败通知 + 保留期清理——复用 cron_runs 生命周期模式）。
- 备份目标：本地轮转 + S3 兼容对象存储直连（云 OSS/阿里 OSS；MinIO 仅自托管选项，见第七节）。
- 恢复演练文档与一键恢复脚本；**平台自身备份**（DB + compose 目录 + 密钥导出/恢复）一并做。

### 7. AI 顾问层试点（主线地基｜自用与叙事并重，见第五节）
- 两个场景先行：告警诊断摘要、蓝绿/部署变更审核建议。

## 四、P6（按需启动）

- **AI 对话 UI（首项，旗舰体验：通用模式 + 平台上下文挂载）与平台 MCP Server 化**（见第五节）。
- **配置拉取 API（方案 B，2026-10-03 细化）**：服务启动时 `GET /api/config/{app}/{env}` 获取整合后配置——**复用文件形态真相源**（版本/脱敏/审计全部沿用），不引入新组件。要点：
  - 聚合语义：按"应用"归组同环境多文件（app.yaml + mysql.yaml → 深合并单文档）；合并冲突 key 报错拒绝；仅同格式可合并（yaml/json/toml 结构合并，env/ini 按 key 平铺合并）；响应带 `X-Config-Version`（各文件 hash 聚合指纹）供客户端侧缓存/变更检测。
  - 鉴权：应用级 token（管理后台签发，只读限定 app×env 范围），不做用户 token 复用（服务间凭证与人凭证分离）。
  - 与下发的组合：同一份配置既能 SFTP 下发（文件消费）也能 API 拉取（启动消费）；拉取不经过远端文件，直接读平台库当前版本。
  - 缓存：API 侧 60s 短缓存 + ETag；不做推送/长连接（热更诉求留给 SDK 形态评估）。
  - **决策点（P6 计划时定）**：本方案落地后 AgileConfig 的必要性收缩为"多语言 SDK 生态 + 推送热更"——若自用场景不需要，AgileConfig 可整体降为 P7+/不做（rule of two：文件下发 + API 拉取已构成两种消费形态，第三种消费形态才需要新抽象）。
- AgileConfig 服务发现（compose 期可选能力）。
- IM 机器人双向（查状态/确认告警，与 AI 对话入口融合）。
- AI 自然语言 → 操作（带人工确认层）。
- k3s 主线（触发判据满足后另立计划）。
- 前端技术债收口（#33 composable 抽取等）。

## 五、AI 规划（主线，分两批 + 对话 UI）

### 架构底座（P5 落地）
- **AI 中转层**：后端模块（OpenAI 兼容协议），provider/model/endpoint/key 可配置；审计与用量记录；与 AgileConfig 中转共用鉴权/脱敏基建。
- **上下文供给层（Context Pack）**：平台把特权上下文打包成结构化供给——主机清单/状态、项目与发布历史、容器与指标、cron 输出与审计、配置快照、告警事件。**这是本平台做 AI 的护城河：通用助手要用户贴日志，我们手里有全量结构化上下文。**

### 主线轨迹声明
P1~P5 的运维功能是 AI 主线的**地基**（数据、通道、审计、上下文），P5 铺中转层与 Context Pack（只读版），**P6 起 AI 成为主线功能**：对话 UI（P6 首项，旗舰体验）与 NL→操作。

### 场景批次
- **第一批（advisory，P5）**：告警诊断摘要（通知附带上下文打包 + AI 归因建议）；变更审核（compose diff 审查：healthcheck 缺失/端口冲突/资源限制/迁移风险）；失败归因与模板生成（cron 脚本/告警模板/compose 片段）。
- **第二批（确认层，P6）**：自然语言 → 平台操作（解析为待执行操作，人确认后走既有权限与审计执行）。

### Skill 与 MCP 生态接入（管理员可配置，2026-09-28 补充决策）

结论：**采纳，并升格为 AI 架构的标准形态**——平台工具协议不自研私有格式，统一走 MCP；
这同时回答了"AI 串联功能"的实现载体。平台在 MCP 生态中扮演**双重角色**：

1. **平台作为 MCP Server**（P6，与对话 UI 同期——对话 UI 本身就是"内置 MCP 客户端 + 界面"）：
   - 平台能力暴露为标准 MCP tools：查主机/容器/指标、查发布与 cron 历史、读日志尾部、
     （确认层）触发操作。Context Pack 的供给与角色过滤也在 tools 层实现，一套协议两处复用。
   - 开源视角的放大器：Claude Desktop / IDE / 任意 MCP 客户端可直接接入 CustosMachina，
     对话 UI 不是唯一入口。
2. **平台作为 MCP Client**（P6 末~P7）：管理员在后台注册外部 MCP servers
   （HTTP Streamable 传输为主；stdio 仅限后端本地拉起，单镜像部署下受限支持），
   对话 Agent 可调用外部工具（拨测查询、文档检索等）。

**Skill = 管理员配置的声明式技能包**：Markdown+frontmatter（或 YAML）描述的
提示词模板 + 工具组合 + 运维 runbook，会话中按名调用（如 @故障排查 / @发布检查）。
**只做声明式，不做代码执行型 skill**（安全边界：skill 不携带可执行代码）。

**管理配置面**（admin）：MCP server 注册表（endpoint/传输/密钥）、启用范围（全局/角色）、
**工具 allowlist 按角色过滤**（与 Context Pack 角色过滤同套机制）、写操作工具默认挂确认层。
**技术选型**：Go 官方 modelcontextprotocol SDK（或 mark3labs/mcp-go）；纪律：不自研 Agent
编排框架，调度交给模型端。

### 独立对话 UI（DeepSeek 网页形态，用户 2026-09-28 补充规划）
- 纯对话前端：流式输出（SSE）、多会话管理、Markdown/代码块渲染。
- 双模式：
  - **通用 Agent 对话**：不接平台数据，纯模型对话（也用于配置调试）。
  - **平台上下文对话**：会话可挂载 Context Pack（选择项目/主机/时间窗），AI 回答基于平台实时数据；后续演进为对话内工具调用（只读查询先行，写操作走确认层）。
- 前端组件复用：Monaco（代码块编辑）+ 通知路由（对话中触发的告警查询）。
- 实施顺序与落点：中转层 + Context Pack 只读版（**P5 末**）→ 对话 UI（**P6 首项**，含通用模式与平台上下文挂载）→ 顾问场景挂接。
- **技术设计先行**（一页文档，动手前评审）：流式 SSE 穿中转层的超时/背压/goroutine 生命周期治理（单实例 + 日志 follow 死锁前科，见审核留档）；Context Pack 的角色过滤与 DLP 实现点。

## 六、生态通用化（开源适配层，用户 2026-09-28 补充规划）

目标：作为开源项目让更多人可用，把强绑定生态改为**可插拔 provider**。原则：接口在本仓定义，适配器按需注册，能力探测 + 配置驱动，未配置时优雅降级。

| 绑定点 | 现状 | 通用化方向 | 优先级 |
|---|---|---|---|
| Git 服务（CI 源） | gitea 原生 API + webhook 兼容层 | GitProvider 接口（gitea/forgejo/gogs API 高度兼容，一家适配器通吃） | 高（开源用户第一门槛）。GitHub/GitLab 适配器已砍（2026-10-05：GitLab 重型组件不合定位；见 P6 计划 M9 裁定） |
| IM 通知 | 企微/钉钉/飞书三家 | 已是插件式；补 Telegram/邮件(SMTP) 适配器 | 高（海外用户） |
| IM 扫码登录 | 企微 CorpApp / 钉钉 | 不再扩展外部 OAuth（2026-10-05 砍 GitHub OAuth：内部平台用户/权限不可控，账号生命周期必须由企业管理） | 中 |
| 观测后端 | OpenObserve | ObservBackend 接口（告警模板/日志查询/外链生成） | 中（P5 先写 O2 具体实现；Grafana/Loki 需求出现再抽接口） |
| 配置中心 | AgileConfig（P5 接入） | **不预期第二实现，不抽 ConfigProvider 接口**（多生态明确不做，决策记录见下）；唯一"免费"的第二形态是转 k3s 后的 ConfigMap | 高（决策记录见下） |
| 对象存储 | （P5 备份引入） | S3 兼容协议为标准（MinIO/云 OSS/阿里 OSS 全覆盖），无需多适配 | 低 |
| ACME DNS | lego 自带全量 provider | 无需自研 | — |
| 镜像仓库 | docker registry 协议 | 已通用（harbor 等兼容） | — |

**抽象纪律（rule of two）**：接口在**第二个实现确定要来时才抽**——ObservBackend 一期只有一个实现，先写具体代码；GitProvider 是例外（gitea/forgejo/gogs 兼容性确定，值得先抽）。**ConfigProvider 是"判定不该来"的例外**（见决策记录）。另注意 GitHub 适配器工作量远大于表格观感（webhook 语义、状态回写、token 模型差异），排期时单列。

**AgileConfig 决策记录（2026-10-01 定稿）**：配置版图只做两个实现，且各有明确存在理由——**文件级配置内建**（配置文件管理模块，零新增部署拓扑，覆盖 compose 期 80% 场景）+ **K/V 拉取式外接 AgileConfig**（轻量外部服务，覆盖 SDK 热更/多应用共享配置场景），两者互补而非二选一。**多配置中心生态明确不做**：轻量级赛道 AgileConfig 几乎无等量竞品；Nacos/Apollo 等与"单实例轻量"初衷冲突（一套 Java 栈比平台本身还重）；Consul/etcd 派无可中转的管理面；k3s 后 ConfigMap 是免费答案。用户自装 Nacos 等不受影响——平台的配置文件管理仍可向其挂载的配置文件写入。实施纪律：中转层的存储与 UI 模型以平台自有概念（应用/环境/键值/版本/审计/脱敏）为准，**前端与 API 只面向平台模型，AgileConfig 是可替换的后端 provider**（用户明确要求"UI 不变、只换底层"）——AgileConfig 特有概念（节点/客户端在线状态）降级为可选能力，不让其渗入模型；此 provider 接缝是 rule of two 的正当例外（服务于已明确的换底需求，非投机抽象）。止损判据保留：若 AgileConfig OpenAPI 覆盖度不足密钥级权限控制，则 K/V 场景回退内建轻量存储。

**开源化前置项**：版本化 migration 策略（当前仅 AutoMigrate，多用户后 schema 变更是事故现场——遗留 #9 延伸）；依赖 license 审计与贡献者协议；部署文档参数化（生态选择矩阵）、种子数据中立化、README 英文化。

## 七、生态接入候选（仅轻量级，2026-09-28 评估）

## 八、不做清单（有意取舍，防范围蔓延）

工单/变更审批流、多租户、成本管理、漏洞扫描、CMDB 自动发现、SLA 管理、jumpserver 级堡垒能力（MFA/双人复核/授权窗口）、自研告警引擎、自研 ACME、内嵌重型平台 UI、链路追踪（业务接 OTel 前）、平台多实例 HA（需求出现前）。

## 九、执行纪律

- 每阶段：详细计划文档（**须含可判定的验收标准**，如"告警从触发到 IM 送达 ≤ 30s"）→ 实施 → 深审 → 真机 + UI 双验证 → 收尾评审（沿用 P4 质量闭环）。
- 优先级冲突时：**备份/数据安全 > 通知/告警（知情权）> 自动化便利 > 界面体验**。
- 新功能一律过"开源适配层"审视：按第六节 rule of two 执行（第二个实现确定要来才抽接口）。

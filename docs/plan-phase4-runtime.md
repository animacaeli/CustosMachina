# 第四阶段计划：运行时分界（compose 收尾 + 定时任务/脚本库/观测部署/SFTP + k3s 主线）

> 状态：**执行中**（v1.1，2026-09-26 起草，2026-09-27 自审修订：观测里程碑编号修正、补调度错失/并发策略与脚本类型×载体矩阵、明确蓝绿回滚不对称与长连接 drain 局限、SFTP dev 权限定死；同日实施 M1~M5 全部完成，实现要点见各 commit 与 docs/deploy-conventions.md；蓝绿实施时修正了"灰度与蓝绿共写同一 conf"的单写者问题——整份渲染收敛到 canary 模块）
> 前置：第三阶段（环境管理 M0~M5 + 真机 e2e）已完成，deploy/日志/伸缩/灰度渲染四接口已按 compose/k3s 双形态设计。
> 本阶段要回答的三个问题：**compose 期做到什么程度、什么时候转 k3s、哪些功能值得在 compose 期做**。

## 一、总判断：compose 的能力边界

e2e 联调后可以明确划线。compose 期已经**做对了**且够用的：部署（gitops-lite 按标签取 compose）、隔离域（项目名前缀）、伸缩、日志、灰度分流片段。compose 期**结构性做不了**（做了就是自建半个 K8s）的：

| 能力 | compose 现状 | 自建代价 | k3s 内置 |
|---|---|---|---|
| 滚动更新 | `up -d` 重建，无健康检查驱动 | 蓝绿双域（本阶段 M2，见下） | Deployment 原生 |
| 服务发现/网络 | external network + 容器名，隐式约定 | 文档问题非代码问题 | Service/DNS 原生 |
| nginx 全量管理 | 仅灰度分流片段（conf.d + reload） | 自建半个 ingress controller | ingress + 原生流量切分 |
| 多机监控/日志部署 | 逐台部署 | 每台手工（本阶段模板化解决） | DaemonSet 一行 |
| 定时任务竞态 | 无 | 一次性容器语义（本阶段实现） | CronJob 原生 |

**结论**：上表左三项不自建，维持现状并文档化约定；后两项在 compose 期以"语义对齐 K8s"的方式实现（一次性容器 = CronJob、模板部署 = DaemonSet 的手动版），迁移时只换执行器、不动模型。

## 二、转 k3s 的时机（判据，而非日期）

满足**任意两条**即启动 k3s 主线：

1. 受管主机 ≥ 3 台且有多机部署需求（单机 compose 的场景消失）；
2. 出现第一个真实的滚动更新/健康检查驱动的发布需求；
3. 业务服务实例数需要弹性（节点资源不均、需要调度）；
4. 观测组件部署超过 ~5 台主机（逐台维护成本超过学习 k3s 的成本）。

当前状态：1 台云服务器 + 本机，**均未触发**。所以 k3s 是本阶段的"主线预备"（接口已备好），不是立即切换。防止的两种偏差：在 compose 上造轮子（已划线不做），以及在触发条件满足后继续把 compose 功能堆深。

## 三、compose 期短项（本阶段主体）

### 1. 定时任务 + 脚本库（合流做一个模块）——价值最高

**模型**（语义对齐 K8s CronJob，k3s 迁移只换执行器）：

- `cron_scripts` 表：名称、类型（shell / python / compose-run）、内容或命令、超时、备注；仅 admin 可建可改；
- `cron_jobs` 表：绑定脚本 + cron 表达式或固定间隔 + 目标主机 + 执行容器镜像/服务（一次性容器：`docker run --rm <镜像> <子命令>` 或 `docker compose run --rm <svc>`）+ 启用开关；
- 调度：平台 `jobs` 框架统一调度（平台单实例 = 调度权威，无竞态）；到点经 SSH 在目标机起一次性容器，容器销毁即任务结束；
- 执行历史：`cron_runs` 表（状态/输出/耗时），输出回平台留痕——不依赖目标机日志；
- 手动触发：脚本库页面可立即跑一次（复用同一条执行链路）；
- 安全：脚本创建/修改/触发均 admin；每次执行落审计事件；执行超时强杀。

**调度语义**（对齐 K8s CronJob，M1 前定死、不在实现时临场拍板）：

- **错失策略（missed run）**：跳过不补跑。平台重启/宕机期间错过的触发点不补偿，恢复后按下一个到点正常调度；调度器启动时若发现任务上次"运行中"状态悬空（平台宕机前发起、结果未知），落一条 `cron_runs` 记录标记 `unknown`，不自动重跑。理由：补跑语义在幂等性未知的前提下不安全，跳过与 K8s CronJob 默认方向一致，实现最简。
- **并发策略（concurrency）**：`Forbid`——同一任务上一次执行未结束时，下一个到点跳过并落一条 `skipped` 记录（输出注明因并发跳过）。不做 Allow/Replace，需要并行跑的任务应拆成多个任务。
- **调度实现**：现有 `pkg/jobs` 框架只有固定间隔 Ticker，不支持 cron 表达式。不改造框架，而是注册一个**扫描型 Job**（30s 间隔）：每轮查 `cron_jobs` 中启用且到点的任务（下次触发时间由 robfig/cron 解析表达式预计算落库），到点即分发执行并更新 `next_run_at`。好处：调度权威仍是单实例平台、错过判定（`next_run_at < now` 且超过宽限即记 missed）有明确落点，任务增删改不需要重启调度 goroutine。
- **脚本类型 × 执行载体**的对应关系（`cron_scripts.type` 与 `cron_jobs` 执行载体的合法组合）：

| 脚本类型 \ 执行载体 | `docker run --rm <镜像>` | `docker compose run --rm <svc>` |
|---|---|---|
| shell | ✅ 跑在绑定镜像内（镜像须含 sh；python 同理走 `/bin/sh -c`） | ✅ 跑在项目 compose 定义的服务环境内（可用其 env/挂载） |
| python | ✅ 镜像须含 python3，脚本内容写入容器执行 | ✅ 同上，项目镜像含 python3 |
| compose-run | ❌ 不适用 | ✅ 即项目内定义好的命令型服务，脚本字段仅存备注/命令 |

定义任务时按此表校验非法组合，避免"shell 脚本 + 无 shell 镜像"之类的运行期失败。

**对编译型语言的回答**（评估结论）：不需要独立产物——同一业务镜像 + 子命令（`app cron cleanup`），Python 项目挂载脚本或脚本进镜像。user-manage-v2 类"主服务内嵌定时"的迁移路径就是把 ticker 逻辑抽成子命令。

- 里程碑 **M1**（约 1 周）：模块 + 调度 + 执行历史 + 前端（脚本库页 + 任务列表 + 运行历史抽屉）。

### 2. 蓝绿发布（不停机更新）——复用现有机制的自然组合

**决策（2026-09-26）**：对"compose 不自建滚动更新"的划线做修正——蓝绿不是自建滚动控制器，
是多隔离域部署 + nginx conf 自动写入 reload + 健康探测三个已有零件的编排，成本可控。

**流程**（发布按钮背后的一条链，全程 API 化）：

1. 部署新颜色域 `<proj>-prod-green`（`up -d --wait`，compose healthcheck）；
2. 健康门禁：循环探测全部服务 healthz，失败则**发布中止**（新版本起不来时线上零影响——这是 `up -d` 原地重建给不了的）；
3. 渲染整份 `<proj>.conf` 覆盖写入（upstream blue/green + map 指向活跃色），`nginx -t` 通过才 reload；test 失败自动恢复备份的旧 conf（nginx reload 失败本就不影响运行中配置，双保险）；
4. drain 窗口（默认 30s，可配）：存量连接在旧颜色上跑完。注意 drain 只对短连接/空闲连接有效，
SSE/WebSocket 等长连接不会自然结束，超时后随旧颜色域销毁被硬切——因此接入规范要求长连接
客户端实现重连（见前提条件）；
5. 销毁旧颜色域，落发布记录。

**nginx 自动化要点**（`DeployNginxConf` 已具备，蓝绿推广）：
- 每次切换都 reload → upstream 域名重新解析，不需要脆弱的 resolver 运行时解析配置；
- 先起容器再写配置（upstream 引用的容器名必须已可解析，`nginx -t` 天然拦截残缺配置）；
- conf.d 覆盖式整文件渲染，幂等无状态；
- 约束：nginx 容器与业务容器同 external network（既有接入规范）。

**前提条件**（项目接入规范，文档化）：入口走反代不占宿主端口；服务定义 healthcheck；
无状态（会话外置）；应用处理 SIGTERM 优雅退出；DB 迁移向后兼容（双域共存期共用存储）；
长连接服务（SSE/WebSocket）需客户端实现重连。

**回滚的不对称性（明确预期，不承诺"无脑回滚"）**："发布即回滚"的前提是新版本
DB 迁移**只加不改不删**（加表/加可空列）。若发布走了改/删类迁移，切回旧色可能
与旧代码不兼容，此时回滚需人工评估 DB 状态——发布记录中记录本次发布是否包含
迁移及迁移类型，回滚操作在界面上对此类发布给出提示而非直接放行。

**附带收益**：发布即回滚（切回旧颜色域）；切换失败自愈（旧颜色未销毁前始终可用）。

- 里程碑 **M2**（约 3-5 天）：颜色域管理、健康门禁、conf 渲染切换、drain/回收、发布记录串联。

### 3. 观测组件一键部署——工作量最小、日常价值大

- 内置 compose 模板：cadvisor（版本固定，注明半弃维护、k3s 期被 kubelet cAdvisor 淘汰）、vector（docker source 采容器日志，输出指向平台配置的 O2 地址）；
- "观测组件"页面：选目标主机 → 一键部署/升级/卸载；部署前环境探测复用 M4 能力；
- 模板内容后端配置化下发（同安装引导文案的约定），版本升级 = 换模板重部署；
- 顺带探测 O2 agent（OTEL collector）存在性，为后续"平台代装采集端"留位。
- 里程碑 **M3**（约 2~3 天）。

### 4. SFTP 文件管理

- `github.com/pkg/sftp` 架在现有 SSH 连接池与凭据体系上（零新增认证面）；
- 功能：目录浏览、上传、下载、重命名/删除、小文件在线编辑（编辑走审计）；
- 权限：随主机管理权限——admin/ops 可写；**dev 只读浏览**（定死的决策，不再"可选"：
  浏览目录结构对排查问题有价值，写权限则与角色模型冲突）；
- 里程碑 **M3**（约 3 天，主要在 UI）。

- 运行时适配器：deploy/实例日志/伸缩已有接口，补 k3s 实现（client-go）；`project_env_targets.runtime=k3s` 字段已预留，按项目共存（第三阶段既定决策）；

## 六、风险与开放问题

1. **一次性容器的镜像依赖**：compose-run 依赖项目 compose 里有任务服务定义；`docker run` 依赖镜像可拉取（镜像仓库可达性）。执行器两个都支持，任务定义时二选一。
2. **python 脚本的运行环境**：目标机需 python3（环境探测顺带确认）；脚本依赖第三方库的场景引导用户走"脚本进镜像"。
3. **cron 表达式解析**：引入 `github.com/robfig/cron/v3`（MIT、Go 生态事实标准、无传递依赖）。注意只用它的**解析器**（`cron.ParseStandard` + `Schedule.Next`）计算 `next_run_at`，不用它的调度器——调度权威保持是平台的扫描型 Job，避免两套调度并存。支持 5 段式 + `@every`。
4. **SFTP 大文件传输**：走 SSH 通道限速于带宽；>100MB 提示走 scp/直传（不做成网盘）。
5. **k3d 与 docker desktop 的兼容性**：k3d 在 mac docker 上成熟；触发主线时先做 0.5 天验证（选无外部依赖的测试项目即可，风险低）。

# 第四阶段计划：运行时分界（compose 收尾 + 定时任务/脚本库/观测部署/SFTP + k3s 主线）

> 状态：**待评审**（v1，2026-09-26 起草）
> 前置：第三阶段（环境管理 M0~M5 + 真机 e2e）已完成，deploy/日志/伸缩/灰度渲染四接口已按 compose/k3s 双形态设计。
> 本阶段要回答的三个问题：**compose 期做到什么程度、什么时候转 k3s、哪些功能值得在 compose 期做**。

## 一、总判断：compose 的能力边界

e2e 联调后可以明确划线。compose 期已经**做对了**且够用的：部署（gitops-lite 按标签取 compose）、隔离域（项目名前缀）、伸缩、日志、灰度分流片段。compose 期**结构性做不了**（做了就是自建半个 K8s）的：

| 能力 | compose 现状 | 自建代价 | k3s 内置 |
|---|---|---|---|
| 滚动更新 | `up -d` 重建，无健康检查驱动 | 高且不可靠 | Deployment 原生 |
| 服务发现/网络 | external network + 容器名，隐式约定 | 文档问题非代码问题 | Service/DNS 原生 |
| nginx 全量管理 | 仅灰度分流片段（conf.d + reload） | 自建半个 ingress controller | ingress + 原生流量切分 |
| 多机监控/日志部署 | 逐台部署 | 每台手工（本阶段模板化解决） | DaemonSet 一行 |
| 定时任务竞态 | 无 | 一次性容器语义（本阶段实现） | CronJob 原生 |

**结论**：上表左三项不自建，维持现状并文档化约定；后两项在 compose 期以"语义对齐 K8s"的方式实现（一次性容器 = CronJob、模板部署 = DaemonSet 的手动版），迁移时只换执行器、不动模型。

## 二、转 k3s 的时机（判据，而非日期）

满足**任意两条**即启动 k3s 主线：

1. 受管主机 ≥ 3 台且有多机部署需求（单机 compose 的场景消失）；
2. 出现第一个真实的滚动更新/健康检查驱动的发布需求；
3. 业务服务实例数需要弹性（节点资源不均、需要调度）；
4. 观测组件部署超过 ~5 台主机（逐台维护成本超过学习 k3s 的成本）。

当前状态：1 台云服务器 + 本机，**均未触发**。所以 k3s 是本阶段的"主线预备"（接口已备好），不是立即切换。防止的两种偏差：在 compose 上造轮子（已划线不做），以及在触发条件满足后继续把 compose 功能堆深。

## 三、compose 期短项（本阶段主体）

### 1. 定时任务 + 脚本库（合流做一个模块）——价值最高

**模型**（语义对齐 K8s CronJob，k3s 迁移只换执行器）：

- `cron_scripts` 表：名称、类型（shell / python / compose-run）、内容或命令、超时、备注；仅 admin 可建可改；
- `cron_jobs` 表：绑定脚本 + cron 表达式或固定间隔 + 目标主机 + 执行容器镜像/服务（一次性容器：`docker run --rm <镜像> <子命令>` 或 `docker compose run --rm <svc>`）+ 启用开关；
- 调度：平台 `jobs` 框架统一调度（平台单实例 = 调度权威，无竞态）；到点经 SSH 在目标机起一次性容器，容器销毁即任务结束；
- 执行历史：`cron_runs` 表（状态/输出/耗时），输出回平台留痕——不依赖目标机日志；
- 手动触发：脚本库页面可立即跑一次（复用同一条执行链路）；
- 安全：脚本创建/修改/触发均 admin；每次执行落审计事件；执行超时强杀。

**对编译型语言的回答**（评估结论）：不需要独立产物——同一业务镜像 + 子命令（`app cron cleanup`），Python 项目挂载脚本或脚本进镜像。user-manage-v2 类"主服务内嵌定时"的迁移路径就是把 ticker 逻辑抽成子命令。

- 里程碑 **M1**（约 1 周）：模块 + 调度 + 执行历史 + 前端（脚本库页 + 任务列表 + 运行历史抽屉）。

### 2. 观测组件一键部署——工作量最小、日常价值大

- 内置 compose 模板：cadvisor（版本固定，注明半弃维护、k3s 期被 kubelet cAdvisor 淘汰）、vector（docker source 采容器日志，输出指向平台配置的 O2 地址）；
- "观测组件"页面：选目标主机 → 一键部署/升级/卸载；部署前环境探测复用 M4 能力；
- 模板内容后端配置化下发（同安装引导文案的约定），版本升级 = 换模板重部署；
- 顺带探测 O2 agent（OTEL collector）存在性，为后续"平台代装采集端"留位。
- 里程碑 **M2**（约 2~3 天）。

### 3. SFTP 文件管理

- `github.com/pkg/sftp` 架在现有 SSH 连接池与凭据体系上（零新增认证面）；
- 功能：目录浏览、上传、下载、重命名/删除、小文件在线编辑（编辑走审计）；
- 权限：随主机管理权限（admin/ops 可写，dev 只读浏览可选）；
- 里程碑 **M3**（约 3 天，主要在 UI）。

### 4. nginx 维持现状 + 约定文档化

不新增功能。补一篇部署文档：external network 约定、upstream 用容器名、灰度片段的 $backend 变量如何在业务 server 块引用。**这半个里程碑是文档不是代码**。

## 四、k3s 主线（触发判据满足后启动，接口已就绪）

- 运行时适配器：deploy/实例日志/伸缩已有接口，补 k3s 实现（client-go）；`project_env_targets.runtime=k3s` 字段已预留，按项目共存（第三阶段既定决策）；
- 灰度：`CanaryRenderer` 的 k3s 实现（ingress 权重 / Gateway API）；
- 定时任务：执行器加"k3s 创建 Job"分支（模型不变）；
- 观测：DaemonSet 替代逐台部署（模板翻译）；
- 测试环境：**本机 k3d**（不占云服务器 2C2G）；迁移试点选一个测试项目（如 tester/demo）双跑验证后切 `runtime=k3s`。
- 不在本阶段排期（触发后再细化计划文档）。

## 六、风险与开放问题

1. **一次性容器的镜像依赖**：compose-run 依赖项目 compose 里有任务服务定义；`docker run` 依赖镜像可拉取（镜像仓库可达性）。执行器两个都支持，任务定义时二选一。
2. **python 脚本的运行环境**：目标机需 python3（环境探测顺带确认）；脚本依赖第三方库的场景引导用户走"脚本进镜像"。
3. **cron 表达式解析**：用robfig/cron 标准库（轻量、Go 生态事实标准），支持 5 段式 + `@every`。
4. **SFTP 大文件传输**：走 SSH 通道限速于带宽；>100MB 提示走 scp/直传（不做成网盘）。
5. **k3d 与 docker desktop 的兼容性**：k3d 在 mac docker 上成熟；触发主线时先做 0.5 天验证（influx 之类无依赖，风险低）。
